# 플래너 할 일 앱 — 요구사항 v3 (신규 개발)

> `[기본값]` 사용자가 달리 정하지 않으면 적용하는 값입니다. 기존 2,496줄 HTML은 화면과 기능의 참고 자료로만 사용합니다. v1 호환과 데이터 마이그레이션은 하지 않습니다.

---

## 0. 전제와 범위

- 신규 개발입니다. 최초 데이터 구조는 `schemaVersion: 1`입니다.
- 실행 환경 `[기본값]`: 사용자 PC에서 여는 단일 HTML 파일. 저장 계층은 어댑터로 분리합니다.
- 동시 편집은 지원하지 않습니다. 여러 탭의 충돌은 감지해서 저장을 막습니다.
- 범위 밖: 서버 동기화, 계정, 알림, 달력, 반복 업무, 하위 업무, 첨부파일, 날짜 변경 이력, IndexedDB 전환.

---

## 1. 기능 요구사항

1. **업무 관리:** 업무마다 제목, 주요 내용을 따로 입력하고 수정합니다. 고유 ID와 생성·수정 시각을 보존합니다.
2. **우선순위:** 등급은 A(매우 중요), B(중요), C(사소)입니다. 세부 순번은 A0(최우선), A1, A2처럼 모든 등급에 붙습니다. 기본 표시 순서는 A → B → C이고, 등급 안에서는 순번을 따릅니다.
3. **순서 변경:** 마우스와 손가락으로 드래그해서 순서를 바꾸고 등급을 옮깁니다. 숫자 입력과 ↑/↓ 버튼으로도 바꿀 수 있습니다.
4. **날짜:** 실행 예정일, 처리기한, 완료일을 구분합니다. 오늘 처리할 업무와 기한이 지난 업무를 표시합니다.
5. **이월:** 미완료 업무를 다음 실행일로 옮깁니다. 같은 세션에서 마지막 이월을 취소할 수 있습니다.
6. **완료:** 완료 체크는 기본으로 숨깁니다. 완료 모드를 켜면 나타납니다. 완료 업무는 기본 화면에서 숨깁니다. 완료 처리와 완료 취소를 명시적으로 할 수 있습니다.
7. **태그와 검색:** 여러 태그를 붙이고, 태그를 눌러 관련 업무만 봅니다. 제목, 내용, 태그로 검색합니다. 등급 탭으로 등급별로 봅니다.
8. **휴지통:** 삭제한 업무는 휴지통으로 옮깁니다. 휴지통에서 복원하거나 영구 삭제합니다.
9. **저장과 백업:** 변경할 때마다 자동으로 저장합니다. 새로고침하거나 다시 열어도 목록이 유지됩니다. JSON으로 내보내고 가져올 수 있습니다.
10. **화면:** PC와 모바일 모두 쓸 수 있는 반응형 화면입니다. 플래너 스타일의 A/B/C 구분을 유지합니다.

## 2. 데이터 모델

### 2-1. 저장 최상위 구조

```
{
  schemaVersion: 1,
  revision: 0,            // 저장할 때마다 1씩 증가
  items: [ ... ]
}
```

### 2-2. 업무 항목

```
{
  id: "task_001",
  title: "보고서 작성",
  body: "관련 자료 검토",
  grade: "A",
  order: 0,
  scheduledDate: "2026-11-17",
  scheduleRevision: 0,
  dueDate: "2026-11-20",
  completed: false,
  completedDate: null,
  tags: ["보고", "검토"],
  deletedAt: null,
  createdAt: "2026-11-16T04:00:00.000Z",
  updatedAt: "2026-11-16T04:00:00.000Z"
}
```

| **필드**                   | **타입**               | **규칙**                                                        |
| ------------------------ | -------------------- | ------------------------------------------------------------- |
| `id`                     | string               | 고유. 중복 금지                                                     |
| `title`                  | string               | 필수. 1\~200자                                                   |
| `body`                   | string               | 0\~20,000자                                                    |
| `grade`                  | "A" \| "B" \| "C"    | 필수                                                            |
| `order`                  | 정수 ≥ 0 또는 null       | 활성 미완료 업무만 정수. 나머지는 `null`                                    |
| `scheduledDate`          | "YYYY-MM-DD" 또는 null | 로컬 날짜                                                         |
| `dueDate`                | "YYYY-MM-DD" 또는 null | 로컬 날짜                                                         |
| `scheduleRevision`       | 정수 ≥ 0               | 실행 예정일(`scheduledDate`) 값이 실제로 바뀐 저장 작업에서만 1 증가. 이월 취소 판정에 사용 |
| `completed`              | boolean              | 완료 여부의 기준 값                                                   |
| `completedDate`          | "YYYY-MM-DD" 또는 null | 완료 업무에서만 값이 있을 수 있음                                           |
| `tags`                   | string[]             | 항목당 최대 20개, 개별 태그 최대 50자. 입력한 표기 그대로 저장                       |
| `deletedAt`              | UTC ISO 시각 또는 null   | 휴지통 이동 시각                                                     |
| `createdAt`, `updatedAt` | UTC ISO 시각           | 모든 시각 필드는 UTC ISO 형식                                          |

### 2-3. 불변조건

| **상태**  | **`completed`** | **`order`** | **`completedDate`** | **`deletedAt`** |
| ------- | --------------- | ----------- | ------------------- | --------------- |
| 미완료 활성  | `false`         | 정수 ≥ 0      | `null`              | `null`          |
| 완료 활성   | `true`          | `null`      | `null` 또는 날짜        | `null`          |
| 미완료 휴지통 | `false`         | `null`      | `null`              | UTC ISO         |
| 완료 휴지통  | `true`          | `null`      | `null` 또는 날짜        | UTC ISO         |

- 같은 등급의 미완료 활성 업무 순번은 **0부터 이어지는 연속된 정수**여야 합니다. 예: 0, 1, 2. 빈 번호가 없어야 합니다.
- 완료 활성 업무는 완료일이 없어도 허용합니다. 이 경우 목록에 "완료일 미기록"으로 표시합니다.

## 3. 저장 계층 (어댑터)

### 3-1. 로드 상태

| **상태**                                        | **처리**                                                           |
| --------------------------------------------- | ---------------------------------------------------------------- |
| `missing` (저장값 없음)                            | 빈 목록으로 시작합니다. 샘플은 만들지 않습니다.                                      |
| `empty` (최상위 객체의 `items`가 빈 배열)               | 빈 목록으로 시작합니다. `[]`, 빈 문자열, 배열만 저장된 값은 여기에 해당하지 않으며 `corrupt`입니다. |
| `ok`                                          | 검증 후 사용합니다.                                                      |
| `corrupt` (파싱 실패, 검증 실패)                      | 복구 모드로 전환합니다. 원본은 건드리지 않습니다.                                     |
| `unsupportedVersion` (`schemaVersion`이 1이 아님) | 복구 모드로 전환합니다. 자동 변환은 하지 않습니다.                                    |
| `unavailable` (저장소 읽기 자체가 예외를 던짐)             | 빈 목록으로 시작하지 않습니다. 저장 불가 안내를 띄우고 모든 쓰기를 막습니다. `missing`과 구분합니다.   |

키가 없는 것(`getItem`이 `null`을 반환)만 `missing`입니다. 접근 예외나 보안 설정으로 인한 거부는 `unavailable`입니다.

### 3-2. `update(expectedRevision, transform)` 계약

- 모든 일반 쓰기는 이 함수 하나를 거칩니다. 복구용 쓰기는 3-3의 전용 경로만 씁니다.
- **최초 저장:** 저장 키가 없으면(`missing`) 논리적 상태를 `{ schemaVersion: 1, revision: 0, items: [] }`로 간주합니다. 최초 저장이 성공하면 `revision`을 1로 기록합니다. 실패하면 저장 키는 없는 상태로 남깁니다.
- **revision 한계:** `revision`이 최대 안전 정수에 도달했으면 증가시키지 않고 `quotaExceeded`가 아닌 `revisionOverflow`로 저장을 차단하고 오류를 안내합니다.
- 실행 전에 저장값을 다시 읽어 최상위 구조와 불변조건을 검증합니다. 실패하면 `corrupt`로 끝내고 아무것도 쓰지 않습니다.
- 복구 모드에서는 이 함수가 `corrupt`를 반환해 일반 쓰기를 차단합니다.
- 실행 순서:
  1. 저장소의 `revision`을 확인합니다. `expectedRevision`과 다르면 `conflict`로 끝냅니다.
  2. 현재 데이터를 깊은 복사합니다.
  3. `transform(copy)`를 호출해 새 데이터 후보를 받습니다. `transform`은 입력을 직접 수정하지 않고 새 후보를 반환해야 합니다.
  4. `transform`이 예외를 던지면 저장하지 않고 `transformFailed`로 끝냅니다.
  5. 후보를 검증합니다. 실패하면 `validationFailed`로 끝냅니다.
  6. `revision`을 1 올리고 저장합니다.
  7. 저장에 성공하면 `{ ok: true, data, revision }`을 반환합니다. 호출부는 이때만 메모리와 화면을 바꿉니다.
- 실패 사유: `conflict`, `transformFailed`, `validationFailed`, `revisionOverflow`, `quotaExceeded`, `unavailable`, `corrupt`, `lockFailed`
- 여러 업무의 순번이 함께 바뀌는 작업(등급 간 이동, 완료 처리, 휴지통 이동·복원 등)은 **하나의 변경 후보를 만들어 `update()`를 한 번만 호출**합니다. 각 단계를 따로 저장하지 않습니다.
- 실패하면 메모리와 화면은 그대로 둡니다. 실패 사유에 맞는 안내를 띄웁니다.

### 3-3. 보조 함수

- `load()`: 3-1의 상태와 데이터를 반환합니다.
- `exportRaw()`: 저장된 원본 텍스트를 반환합니다. 복구 모드에서도 씁니다.
- `restore(validatedBackup)`와 `reset()`: 복구 모드 전용 특수 경로입니다. 일반 `update()`와 분리합니다. 두 함수는 검증과 사용자 확인을 거치며, 쓰기는 어댑터 내부에서만 수행합니다.
  1. 복구 대상 데이터는 메모리에서 먼저 완전 검증합니다.
  2. 덮어쓰기 전에 손상된 원본 텍스트를 **보관 키를 새로 만들어** 복사합니다. 키는 `…-corrupt-<시각>-<짧은 무작위값>` 형식으로 만들며, 기존 보관 키는 절대 덮어쓰지 않습니다. 보관 키를 만들지 못하면 복구를 중단합니다.
     - 보관 키에 기록한 뒤 다시 읽어 원본 문자열과 **정확히 일치하는지** 확인합니다. 일치하지 않으면 내부 보관 실패로 처리합니다.
     - 이 재조회는 기록 내용이 일치함을 확인하는 절차입니다. 저장 장치의 영구 보존을 보장하지 않습니다.
  3. 보관 사본은 자동으로 지우지 않습니다. 목록으로 보여 주고, 사용자가 확인한 뒤에만 정리합니다.
  4. 저장 직전에 대상 키의 현재 원본 문자열을 복구 모드 진입 시 스냅샷과 비교합니다. **다르면 자동으로 덮어쓰지 않고** 충돌을 안내한 뒤 중단합니다. 손상된 원본은 `revision`을 읽을 수 없으므로 문자열 비교를 씁니다. 잠금을 지원하는 환경에서는 `update()`와 같은 잠금 경로를 씁니다.
  5. 저장소 쓰기를 수행합니다. **확정 기준은 이 저장소 쓰기의 성공입니다.**
  6. 쓰기 성공 후 화면 갱신이 실패해도 저장 실패로 되돌리지 않습니다. 저장된 상태를 다시 로드해 화면을 맞춥니다.
  7. 쓰기 자체가 실패하면 원본과 복구 모드를 그대로 둡니다.
- 문자열 비교와 저장은 원자적이지 않습니다. 잠금을 지원하지 않는 환경에서는 이 검사가 최선 노력 수준입니다.
- 보관 사본 생성이 실패하면 기본 정책은 복구 중단입니다. 이때 사용자가 원본을 파일로 내보내거나 텍스트로 복사해 **외부에 보존했다는 확인 체크를 직접 한 경우에만** 내부 사본 없이 복구를 진행할 수 있습니다. 복사 버튼을 누른 사실만으로는 외부 보존이 완료됐다고 보지 않습니다.
- 저장 성공 후 UI 처리에서 예외가 났다는 이유만으로 원본이 보존됐다고 판단하지 않습니다. 원본 보존 여부는 2번 단계의 보관 키로 확인합니다.
- **일반 JSON 가져오기:** 정상 모드에서 쓰는 경로입니다. 가져온 파일을 검증한 뒤 "현재 데이터를 대체합니다" 확인을 거쳐 `update()`로 전체 데이터를 교체합니다. `expectedRevision`은 현재 저장소의 `revision`을 씁니다. 가져온 파일의 `revision`은 충돌 검사에 쓰지 않고, 저장 시 현재 `revision`에 1을 더한 값을 부여합니다. 검증 실패 시 기존 데이터는 그대로 둡니다.
- **가져오기 시 전체 정합성 검증:** 가져온 파일은 최상위 스키마와 4-2의 항목별 불변조건을 모두 통과해야 합니다. 하나라도 실패하면 교체하지 않습니다.
- **가져오기·복원 후 이월 취소 무효화:** 가져오기나 복구 복원이 성공하면 세션에 보관된 이월 취소 기록을 지웁니다. 교체된 데이터에 대해 이전 이월을 취소하지 않도록 하기 위해서입니다. 가져온 업무의 `scheduleRevision`은 유효한 값이면 그대로 보존합니다.
- **가져오기 경로 요약:** 정상 모드 가져오기는 `update()`, 복구 모드 가져오기는 `restore()`, 초기화는 `reset()`을 씁니다.
- 잠금: 환경이 지원하면 `update()` 안에서 잠금을 잡습니다. 지원하지 않으면 충돌 감지는 최선 노력 수준입니다.

## 4. 데이터 보호 (P0)

### 4-1. 복구 모드

- 추가, 수정, 삭제, 완료, 드래그, 이월, 휴지통 복원 등 **일반 업무 쓰기를 막습니다.** 아래 허용 동작의 검증된 복구·초기화만 예외로 허용합니다.
- 허용 동작:
  1. 원본 파일 내보내기
  2. 원본 텍스트 복사
  3. 검증된 JSON 백업 가져오기. 검증과 저장이 모두 성공하면 복구 모드를 해제합니다.
  4. 명시적 초기화
- 초기화 조건: 원본을 내보내거나 복사한 뒤, "원본을 저장했습니다" 확인 체크를 하고, 영구 삭제 경고에 최종 확인해야 합니다.
- 초기화가 실패하면 손상된 원본과 복구 모드를 유지합니다.

### 4-2. 검증 규칙

| **검사**    | **기준**                                                                                |
| --------- | ------------------------------------------------------------------------------------- |
| 최상위       | 객체이고 `schemaVersion === 1`, `revision`은 0 이상의 안전한 정수, `items`는 배열입니다                  |
| 항목 구조     | 각 항목은 객체입니다. `null`은 허용하지 않습니다                                                        |
| ID        | 중복이 없어야 합니다                                                                           |
| 등급        | A, B, C 중 하나입니다                                                                       |
| 제목·내용     | 제목 1\~200자, 내용 0\~20,000자                                                             |
| 날짜        | `null` 또는 `YYYY-MM-DD` 형식이며, 실제 달력에 존재하는 날짜여야 합니다 (예: `2026-02-30`은 실패)               |
| 실행 예정일 버전 | `scheduleRevision`은 0 이상의 안전한 정수입니다                                                   |
| 시각        | `createdAt`, `updatedAt`은 파싱 가능한 UTC ISO 8601 문자열이고, `deletedAt`은 `null` 또는 그런 문자열입니다 |
| 태그        | 문자열 배열이고 개수와 길이 제한을 지킵니다                                                              |
| 불변조건      | 2-3의 상태표를 따릅니다                                                                        |
| 순번        | 같은 등급의 미완료 활성 업무가 0부터 연속된 정수입니다                                                       |

검증 하나라도 실패하면 `corrupt`로 처리합니다.

### 4-3. 경계 조건

| **상황**                               | **처리**                                                  |
| ------------------------------------ | ------------------------------------------------------- |
| `schemaVersion`이 1보다 큰 정수            | `unsupportedVersion`, 복구 모드                             |
| `schemaVersion`이 없거나, 정수가 아니거나, 0 이하 | `corrupt`, 복구 모드                                        |
| `revision`이 최대 안전 정수                 | 증가 전에 저장 차단, `revisionOverflow` 안내                      |
| 이월 후 업무가 완료되었거나 삭제됨                  | 자동 취소하지 않고 충돌 목록에 표시                                    |
| 휴지통의 완료 업무 복원                        | 완료 상태 유지, `order=null`                                  |
| 태그 표기만 바꿈(예: `EMR` → `emr`)          | 업무 변경으로 저장합니다. 비교 키는 유지되고, 대표 표기는 8-3의 선정 기준으로 다시 계산합니다 |
| 로컬 HTML을 `file://`로 직접 열었을 때         | 저장 지속성과 잠금 지원을 가정하지 않고 실제로 시험 (16장 P2 항목)               |

## 5. 날짜, 이월, 이월 취소 (P1)

### 5-1. 판정

| **구분**    | **기준**                            |
| --------- | --------------------------------- |
| 오늘 처리     | `scheduledDate`가 오늘이고 미완료이며 활성 업무 |
| 기한 초과     | `dueDate`가 오늘보다 이전이고 미완료이며 활성 업무  |
| 실행 예정일 없음 | 이월 대상에서 제외합니다                     |

날짜 비교는 로컬 날짜 문자열로 합니다.

### 5-2. 이월

- 대상: 미완료 활성 업무 중 `scheduledDate`가 오늘 이전이거나 오늘인 업무입니다.
- 실행 전에 대상 개수와 변경될 날짜를 미리 보여 줍니다.
- `scheduledDate`만 바꿉니다. `dueDate`는 그대로 둡니다.
- 한 번의 이월을 하나의 실행 단위로 기록합니다.

```
{ action: "rollover", changes: [{ taskId, before, after, scheduleRevisionAfter }] }
```

### 5-3. 이월 취소

- 같은 세션에서 마지막 이월 한 번만 취소할 수 있습니다. 새로고침하면 취소 기록을 지웁니다.
- 각 항목의 현재 `scheduleRevision`이 이월 직후 값(`scheduleRevisionAfter`)과 같고, 현재 `scheduledDate`가 `after`와 같을 때만 `before`로 되돌립니다.
- 이월 취소도 실행 예정일 변경이므로 `scheduleRevision`을 1 증가시킵니다. 이전 버전 번호로 되돌리지 않습니다.
- **증가 규칙:** `scheduledDate` 값이 실제로 달라지는 모든 저장 작업(직접 수정, 이월, 이월 취소)에서만 1 증가합니다. 같은 날짜를 다시 저장하면 증가시키지 않습니다. 제목·내용·태그만 바꾼 경우에도 증가시키지 않습니다.
- 날짜 값만 비교하지 않습니다. 수정 후 같은 값으로 돌아온 경우를 놓치기 때문입니다.
- **부분 충돌 정책:** 되돌릴 수 없는 항목은 조용히 건너뛰지 않고 충돌 목록으로 보여 줍니다. 기본 동작은 충돌 없는 항목만 되돌리고, 충돌 항목은 이월 상태를 그대로 둡니다.
- 실행 전에 복구 대상과 제외 대상을 함께 미리 보여 줍니다. 사용자가 확인하면 하나의 `update()`로 저장합니다. 제외된 항목의 날짜는 사용자가 항목별로 따로 정합니다.
